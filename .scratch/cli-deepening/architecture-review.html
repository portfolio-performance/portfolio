After: one deep module, operations call one interface

▼ ▼ ▼ ▼

Transaction records · interface

records(client) · render(record) · build(json) · update(record, patch) · delete(record)

internal

side join + batch index per-type member rules → refusals + help prose one parser shape (read/write) copy onto existing sides oversell guard
Problem
The Transaction record is split over ~12 modules in two packages. Members are keyed by hand in three places, per-type rules live in prose and code, and update round-trips the read render through Gson to reuse the add path.
Solution
One module owns the side join, shape, member rules, parsing, building and replacing. apply operations and the transactions command become thin callers. OperationContext loses replacing.
Wins
  • Locality: member rules declared once
  • Round trip tested in memory
  • Delete the fake query/apply seam
  • Update stops depending on render
  • One index replaces repeated allOf scans
Tests
TransactionShape, TransactionInput, the side join, OversellGuard and replace have no direct tests today. ~1,500 lines of add/update/delete tests go through CliFixture (XML write, SafeWrite, reload) for each case. After the change: per-type render → build → equal tests at the interface, plus a few CLI smoke tests.
Likely bug found on the way: TransactionUpdates.update (apply/TransactionUpdates.java:61) records type-immutable or kind-immutable on the outer context but still runs the inner add. The inner context counts failures separately, so it can go on to commit the replacement.

Problem
ADR 0005's never-guess rule is enforced three different ways. StrictConverter only gives a right answer if callers reset it and read every lazy core figure before isComplete(); get the order wrong and figures computed at core's 1.0 rate are reported silently.
Solution
One module that a command declares and asks. It owns option, meta, warnings, the strict converter and rate lookup, and takes an injected cache locator instead of the whole CommandContext.
Wins
  • Leverage: one interface, four commands
  • Locality: never-guess lives once
  • Temporal coupling hidden inside
  • Tests skip the 7-arg CommandContext
Tests
StrictConverter and ExchangeRates have no direct tests. With the change, "a figure is left out when a rate is missing" is tested once against in-memory rates, not separately for each command.
Fits ADR 0005: what a total does when a rate is missing can still differ per command. Only rate checking is shared. StrictConverter stays as the adapter over core (ADR 0002), just hidden.

After: CommandSpec is made of facets

facet interface options · meta schema · warnings · errors · putMeta
DateRangePagingSortingfiltersValuation (#2)WriteCommand
command: spec(facets…) + one read per facet
error scope comes from the facets that raise it
Problem
Declaration and execution drift apart. Meta is declared in one place and put by hand in another. Error scope is a hard-coded list of command names, checked only by a source-text regex. ApplyCommand and RestoreCommand repeat the same write scaffolding.
Solution
Use the existing declareIn/putInto pattern of DateRange, Sorting and PerformanceScope everywhere, as one facet interface, and add a WriteCommand facet for dry-run, SafeWrite options, warnings and write errors.
Wins
  • Help follows from use
  • Drop the regex code scan
  • New command: fewer files to touch
  • Facet tests: putMeta matches its schema
Fits ADR 0006: facets produce the CommandSpec, OptionSpec and Schema declarations that help is generated from. No new parser.

Problem
"Write fields are named as in the output" is a convention only. The entity member of a change is a free string, and it has already drifted: the schema at ApplyCommand.java:38 lists four kinds, but TaxonomyOperations.java:83 emits taxonomy-assignment.
Solution
One module per Master data kind holds what is known about it. References, lists, the existing-entity check and entity operations derive from it.
Wins

  • Breaks the command→query cycle
  • Schema catches entity drift

After: each operation declares its failure codes

Problem
Field-level failure codes are part of the interface that agents depend on, but nothing declares them. Help can't list them, and the skill can only say "explain each failure".
Solution
context.fail takes a code declared by the operation or by a shared failure catalog, and help renders the codes for each operation.
Wins
  • Interface becomes discoverable
  • Drift test covers write failures
Same idea as #3 (codes declared by whatever raises them), applied to operations instead of commands. It is cheaper to do after #1, once the transaction codes live in one module.

Problem
Rounding modes are inconsistent: HALF_UP in one place, HALF_DOWN elsewhere, and a share computed with doubles. ADR 0003's sign rule is not enforced in any one place.
Solution
Move these into one small module with direct tests. It is a small module, so check first that it passes the deletion test rather than just moving code.
Wins
  • Rounding tested directly
  • One rate inversion

Top recommendation

1 · Deepen the Transaction record module

It is the hottest code in the history, the least directly tested, and the only candidate with a likely bug in its seam (an update that refuses a type change but still builds the replacement). Making it one module also removes most of the query↔apply cycle and makes #5 cheap.
